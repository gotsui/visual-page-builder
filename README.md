# Web画面構築アプリ

# 基本設計

## 1. システム概要

### 1.1 目的

React / Next.js / TypeScript / Tailwind CSS を用いて、ドラッグ＆ドロップでUI要素を配置し、プロパティを編集しながらレスポンシブなWeb画面を構築できるツールを提供する。
フロントエンド（Next.js）＋ バックエンドAPI ＋ PostgreSQL による構成とする。アプリケーション全体をDockerコンテナで動作させる。


### 1.2 基本方針

- ライブラリ依存を極力最小化する
- 画面構造はツリー構造のノードで表現する
- レイアウトは主にCSS Flexboxで制御する
- デフォルト配置は左上詰めとし、画面単位・グループ単位で中央寄せ・右寄せを可能にする
- グループ化により「行を分けずに要素をまとめる」ことを実現する
- 構築結果はレスポンシブ対応とする

### 1.3 想定利用者

- 画面設計者・フロントエンド開発者
- プロトタイピングや簡易画面生成を行う人

## 2. 機能一覧

|分類|機能|概要|
|-|-|-|

|配置|要素の削除|選択要素の削除|
|グループ|グループ作成・ネスト|複数要素をまとめる（HTMLのdiv相当）|

## 3. 画面構成

画面は大きく3つの領域で構成する。

```
┌─────────────────────────────────────────────────────────┐
│  ヘッダー（プロジェクト名 / 保存 / プレビュー切替 など）   │
├──────────┬──────────────────────────────┬───────────────┤
│          │                              │               │
│ パレット │         キャンバス            │  インスペクタ  │
│          │     （構築中の画面）          │  （プロパティ）│
│ ・テキスト│                              │               │
│ ・ボタン  │                              │  ・内容編集   │
│ ・画像    │                              │  ・スタイル   │
│ ・グループ│                              │  ・レイアウト │
│  など    │                              │               │
│          │                              │               │
└──────────┴──────────────────────────────┴───────────────┘
```

### 3.1 各領域の役割

|領域|役割|
|-|-|
|パレット|配置可能な要素一覧。ここからドラッグしてキャンバスへ追加する|
|キャンバス|実際に画面を構築する作業領域。ドロップ・選択・並び替えを行う|
|インスペクタ|現在選択中の要素のプロパティ・スタイル・レイアウトを編集する|
|ヘッダー|保存・読込・レスポンシブプレビュー切替・全体設定など|

## 4. データモデル設計

### 4.1 基本概念画面
全体をノードのツリー構造で表現する。
- 最上位は常に「ルートコンテナ」
- 各ノードは「種類」「固有プロパティ」「スタイル」「レイアウト設定」「子ノード」を持つ
- グループは「コンテナ種別のノード」として扱う

### 4.2 主要エンティティ
#### ページ（Page）
- ページID
- ページ名
- ルートノード
- ページ全体のレイアウト設定（最大幅、パディング、水平・垂直寄せなど）

#### ノード（Node）
- ノードID（一意）
- 種類（コンテナ / テキスト / ボタン / 画像 / スペーサー など）
- 固有プロパティ（テキスト内容、ボタンラベル、画像URLなど）
- スタイル情報（色、フォント、余白など。レスポンシブ対応のためブレークポイント別に保持）
- レイアウト設定（コンテナのみ有効：方向・寄せ・ギャップなど）
- 子ノード一覧

#### レイアウト設定
- 方向：横並び / 縦並び
- 主軸寄せ：開始（左上） / 中央 / 終了（右下） / 均等配置 など
- 交差軸寄せ：開始 / 中央 / 終了 / 引き伸ばし
- 要素間ギャップ
- 折り返し有無

### 4.3 グループ化の考え方
- グループ ＝ コンテナノード
- 同じ親コンテナ内に複数の子を配置することで「行を分けずにまとめる」
- 縦に並べたい場合は親の方向を「縦」に設定
- 横に並べたい場合は親の方向を「横」に設定
- ネスト（入れ子）を許可し、複雑な構造にも対応

### 4.4 レスポンシブ対応方針
- スタイル情報を「基本」「sm」「md」「lg」などのブレークポイント単位で保持
- プレビュー時に表示幅を切り替えて確認可能にする
- レイアウト設定も必要に応じてブレークポイント別に拡張可能な設計とする

## 5. アーキテクチャ概要

### 5.1 全体構成
- プレゼンテーション：Next.js（App Router）
- アプリケーション／API：Next.js API Routes または別途APIコンテナ
- ドメイン：ノードツリー・ページ構造
- インフラ：PostgreSQL（永続化）、Docker（実行環境）


### 5.2 レイヤー構成

|レイヤー|役割|
|-|-|
|プレゼンテーション|パレット・キャンバス・インスペクタなどのUI表示|
|アプリケーション|ノードの追加・移動・更新・選択などの操作ロジック|
|ドメイン|ノードツリー・レイアウト・ページの構造定義|
|インフラ|ローカルストレージやファイルによる保存・読込（初期は簡易実装）|

### 5.3 状態管理方針
- Reactの標準機能（Context + 状態更新ロジック）を中心に構築
- ノードツリー全体と「現在選択中のノード」を中心に管理
- ライブラリ依存を増やさないことを優先

### 5.4 コンポーネント配置方針
- 要素の種類ごとに「定義情報」（ラベル、デフォルト値、編集可能な項目など）をレジストリとして管理
- 新しい要素を追加する際はレジストリに定義を追加するだけで拡張可能にする

## 6. 主要処理フロー

### 6.1 要素の追加
1. ユーザーがパレットから要素をドラッグ
2. キャンバス上のドロップ可能な領域にドロップ
3. 新しいノードを生成し、対象の親ノードの子として追加
4. 必要に応じて選択状態を新しいノードに切り替える

### 6.2 要素の並び替え・移動
1. キャンバス上の既存要素をドラッグ
2. 別の位置または別の親グループへドロップ
3. ノードツリー上で親子関係と順序を更新

### 6.3 プロパティ編集
1. キャンバス上の要素を選択
2. インスペクタにその要素の編集可能な項目を表示
3. ユーザーが値を変更
4. 対象ノードのプロパティまたはスタイル・レイアウトを更新
5. キャンバスの表示を即座に反映

### 6.4 グループ化
1. 複数要素を選択、または空のグループを追加
2. グループ（コンテナ）を作成し、対象要素をその子に移動
3. グループのレイアウト方向・寄せを設定可能にする

### 6.5 寄せ制御
- ページ全体：ページ設定で水平・垂直の寄せを指定
- グループ単位：そのコンテナのレイアウト設定で寄せを指定
- デフォルトは「開始（左上詰め）」とし、必要に応じて中央・終了に変更

## 7. レイアウト・配置ルール

|項目|ルール|
|-|-|
|基本配置|左上詰め（開始位置）|
|中央寄せ|ページまたはグループの寄せ設定を「中央」にする|
|右寄せ|ページまたはグループの寄せ設定を「終了」にする|
|縦並び|グループの方向を「縦」に設定|
|横並び|グループの方向を「横」に設定|
|行を分けないまとめ|同じ親グループ内に配置する|
|ネスト|グループの中にさらにグループを配置可能|

レンダリング時は主にFlexboxを利用し、上記設定をCSSの配置プロパティに変換して表現する。

## 8. 非機能要件・制約

|項目|内容|
|-|-|
|レスポンシブ|構築した画面は異なる画面幅で適切に表示されること|
|依存ライブラリ|必要最小限に抑える（DnD品質向上と型安全のための最小限の導入は許容）|
|拡張性|新しい要素種類を比較的容易に追加できる構造とする|
|パフォーマンス|ノード数が多くなっても操作が著しく重くならないよう配慮する|
|データ永続化|PostgreSQL|
|実行環境|Dockerコンテナで動作|
|可用性・移植性|Docker Compose等で開発・実行環境を統一|


# 詳細設計

## 1. 詳細設計の位置づけ

データ構造・画面仕様・処理仕様・状態遷移・制約を明確にする。

## 2. データ詳細設計

### 2.1 識別子
- すべてのノードおよびページは一意なIDを持つ
- IDは生成時に一意性が保証される方式で作成する（例：UUID）
- IDは不変とし、変更しない

### 2.2 永続化用エンティティ（DBテーブル相当）

pages テーブル（論理）

|項目|型のイメージ|必須|説明|
|-|-|-|-|
|id|UUID|○|ページ一意識別子（PK）|
|name|文字列|○|ページ名|
|document|JSONB|○|PageDocument全体（rootノードツリーを含む）|
|version|整数|○|データ形式バージョン|
|created_at|日時|○|作成日時|
|updated_at|日時|○|更新日時|
|deleted_at|日時|×|論理削除用（使用する場合）|

- ノードツリーは正規化せず、JSONBカラムにPageDocumentをそのまま格納する方針とする（前回のツリー構造を維持しやすく、変更を最小化するため）。
- 必要に応じて name や updated_at で検索・一覧表示する。

### 2.3 ページ（PageDocument）
|項目|型のイメージ|必須|説明|
|-|-|-|-|
|id|文字列|○|ページ一意識別子|
|name|文字列|○|ページ表示名|
|root|ノード|○|ルートコンテナノード|
|pageLayout|ページレイアウト設定|○|画面全体の配置・余白設定|
|version|数値|○|データ形式バージョン（将来の互換性用）|
|updatedAt|日時文字列|○|最終更新日時|

#### ページレイアウト設定（pageLayout）
|項目|取りうる値|デフォルト|説明|
|-|-|-|-|
|maxWidth|文字列（例: "100%" / "1200px"）|"100%"|コンテンツ最大幅|
|padding|数値（Tailwindのspacing単位相当）|4|外周余白|
|justify|start / center / end|start|水平方向の寄せ|
|align|start / center / end / stretch|start|垂直方向の寄せ|
|background|色指定（任意）|なし|背景色|

### 2.4 ノード（BuilderNode）
|項目|型のイメージ|必須|説明|
|-|-|-|-|
|id|文字列|○|ノード一意識別子|
|type|ノード種別|○|container / text / button / image / input / spacer など|
|props|オブジェクト|○|種別固有のプロパティ|
|styles|レスポンシブスタイル|○|見た目のスタイル（ブレークポイント別）|
|layout|レイアウト設定|△|主にcontainerで使用|
|children|ノード配列|○|子ノード（葉ノードは空配列）|

### 2.5 ノード種別と固有プロパティ
|種別|用途|主な固有プロパティ|子を持てるか|
|-|-|-|-|
|container|グループ（div相当）|なし（または意味付け用のrole）|○|
|text|テキスト|content（文字列）, tag（p/h1/h2/h3/span）|×|
|button|ボタン|label（文字列）, variant（primary/secondary/outline）|×|
|image|画像|src（URL）, alt（文字列）, objectFit|×|
|input|入力欄|placeholder, inputType（text/email/passwordなど）|×|
|spacer|余白|size（数値）|×|

※ 将来の拡張を容易にするため、種別追加時は「定義レジストリ」に追加するだけで対応可能な構造とする。

## 2.6 レイアウト設定（LayoutSettings）※主にcontainer用
|項目|取りうる値|デフォルト|説明|
|-|-|-|-|
|direction|row / column|column|主軸方向|
|justify|start / center / end / between / around|start|主軸方向の寄せ|
|align|start / center / end / stretch|start|交差軸方向の寄せ|
|gap|数値（0以上）|4|子要素間の間隔|
|wrap|true / false|false|折り返しの有無|

### 2.7 レスポンシブスタイル（ResponsiveStyles）
|キー|説明|
|-|-|
|base|すべての画面幅で適用される基本スタイル|
|sm|小さい画面向け上書き（任意）|
|md|中程度の画面向け上書き（任意）|
|lg|大きい画面向け上書き（任意）|

各スタイルオブジェクトに保持する主な項目例：
- width / height / minWidth / maxWidth
- margin / padding（または個別指定）
- backgroundColor / color
- fontSize / fontWeight / textAlign
- border関連
- その他、必要に応じて拡張

### 2.8 選択状態・UI状態
|項目|説明|
|-|-|
|selectedNodeId|現在選択中のノードID（未選択時はnull）|
|hoveredNodeId|ホバー中のノードID（任意）|
|previewMode|edit / preview|
|previewBreakpoint|base / sm / md / lg|
|isDragging|ドラッグ中かどうか|

## 3. 画面詳細設計

### 3.1 全体レイアウト
- ヘッダー：固定高さ
- 左サイドバー（パレット）：固定幅（例: 240px程度）
- 中央（キャンバス）：残り幅をすべて使用。スクロール可能
- 右サイドバー（インスペクタ）：固定幅（例: 300px程度）
- レスポンシブ時はサイドバーを折りたたみ可能とする（詳細は実装時調整）

### 3.2 ヘッダー表示・操作項目：
- ページ名（編集可能）
- 保存ボタン
- 読込ボタン
- プレビューモード切替（編集 / プレビュー）
- ブレークポイント切替（モバイル / タブレット / デスクトップ）
- ページ全体設定を開く導線

### 3.3 パレット
- 配置可能な要素を一覧表示
- 各要素はドラッグ可能
- カテゴリ分け（基本要素 / フォーム / レイアウト など）を推奨
- 表示内容：アイコン + ラベル

### 3.4 キャンバス
#### 表示仕様
- ルートコンテナを起点にノードツリーを再帰的に描画
- 編集モード時は各ノードに選択・ホバー用の視覚的フィードバック（枠線など）を付与
- ドロップ可能な領域を明示（空のコンテナや要素間など）
- プレビューモード時は編集用の装飾を非表示にし、実際の見た目に近づける

#### 操作仕様
- ノードをクリックで選択
- ノードをドラッグして移動・並び替え
- パレットからドロップして新規追加
- 削除はインスペクタまたはキーボード（検討）で実行

#### 配置ルールの反映
- containerのlayout設定をFlexboxの配置に変換して描画
- pageLayoutの寄せ・maxWidth・paddingをルートに適用

### 3.5 インスペクタ
選択中ノードに応じて表示内容を切り替える。

#### 共通セクション
- ノード種別表示
- 削除ボタン
- （containerの場合）レイアウト設定
  - 方向（縦/横）
  - 主軸寄せ
  - 交差軸寄せ
  - ギャップ
  - 折り返し

#### 種別固有セクション
- text：内容テキスト、タグ種別
- button：ラベル、バリアント
- image：画像URL、代替テキスト など
- その他種別も同様

#### スタイルセクション
- 基本スタイル編集
- 必要に応じてブレークポイント別の上書き編集
- よく使う項目を優先表示（余白、色、文字サイズなど）

#### 未選択時
- 「要素を選択してください」などのガイダンスを表示
- またはページ全体設定を表示

## 4. 状態管理詳細設計

### 4.1 管理対象状態
|状態|説明|
|-|-|
|document|現在編集中のPageDocument|
|selectedNodeId|選択中ノード|
|uiState|プレビューモード、ブレークポイント、ドラッグ状態など|

### 4.2 主な操作（アクション）
|操作名|概要|影響範囲|
|-|-|-|
|ノード追加|指定親の指定位置に新規ノードを挿入|document|
|ノード削除|指定ノードをツリーから除去|document / selectedNodeId|
|ノード移動|ノードの親・順序を変更|document|
|ノード更新|props / styles / layout を更新|document|
|選択変更|選択ノードを変更|selectedNodeId|
|ページ設定更新|pageLayout や name を更新|document|
|ドキュメント読込|外部データをdocumentにセット|document / selectedNodeId|
|UI状態変更|プレビューモードやブレークポイント切替|uiState|
|保存|ローカルストレージ／ファイル出力 → API呼び出し → PostgreSQLに保存|
|読込|ファイル／ローカルストレージ入力 → API呼び出し → DBから取得してdocumentにセット|
|新規作成|空のPageDocumentを生成後、初回保存でDBにINSERT|
|一覧表示|DBからページ一覧を取得して選択可能にする|

### 4.3 不変条件
- rootノードは必ず存在し、typeはcontainerとする
- childrenは常に配列（nullにしない）
- 削除時、選択中ノードが削除対象に含まれる場合は選択を解除する
- 移動時、自分自身や子孫を親にできない（循環参照禁止）

## 5. 主要処理詳細

### 5.1 ノード追加処理
1. 追加対象の親ノードIDと挿入位置（インデックス）を決定
2. 種別のデフォルトprops・styles・layoutを取得
3. 新しいIDを発行してノードを生成
4. 親のchildrenの指定位置に挿入
5. 必要に応じて新規ノードを選択状態にする

### 5.2 ノード移動処理
1. 移動元の親から対象ノードを取り除く
2. 移動先の親の指定位置に挿入
3. 移動先が自分の子孫でないことを事前に検証
4. ツリーを更新

### 5.3 ノード削除処理
1. 対象ノードをツリーから再帰的に探索して除去
2. 選択中であれば選択解除
3. ルートノードは削除不可とする

### 5.4 プロパティ更新処理
1. 対象ノードを特定
2. props / styles / layout の該当部分を更新
3. 更新後のツリーでキャンバスを再描画

### 5.5 ドロップ位置の決定ロジック（概念）
1. 空のcontainer上 → そのcontainerの末尾（または先頭）に追加
2. 既存ノードの前後 → 同じ親の前後の位置に挿入
3. 別のcontainer内 → そのcontainerの子として追加
4. 無効なドロップ先（自分自身の中など）は拒否

### 5.6 レンダリング変換ルール
1. container → Flexコンテナとして描画し、layoutをCSSに反映
2. text → 指定タグでテキスト描画
3. button → ボタン要素として描画
4. image → img要素として描画
5. その他 → 種別に応じた要素
6. stylesは現在のプレビューブレークポイントを考慮して適用

## 6. レスポンシブ詳細設計

### 6.1 ブレークポイント定義（目安）base：デフォルト（モバイル基準を推奨）
- sm：小さい画面
- md：中画面
- lg：大きい画面

※ 具体的なピクセル値はTailwindの標準に合わせる。

### 6.2 適用ルール
- 基本はbaseのスタイルを適用
- より大きいブレークポイントの指定がある場合は上書き
- プレビュー時は選択中のブレークポイントに合わせてキャンバス幅を変更し、該当スタイルを適用

### 6.3 編集時の扱い
- インスペクタでは主にbaseを編集
- 必要に応じてブレークポイント別タブまたはセクションで上書き編集可能とする

## 7. データ入出力設計
- 保存先：PostgreSQL
- インターフェース：HTTP API（REST想定）GET /api/pages … 一覧取得
  - GET /api/pages/:id … 単一取得
  - POST /api/pages … 新規作成
  - PUT /api/pages/:id … 更新
  - DELETE /api/pages/:id … 削除

- リクエスト／レスポンスの中心データは前回定義のPageDocument（JSON）
- エラー時は適切なHTTPステータスとメッセージを返却

## 8. エラー・例外・制約
|ケース|対応方針|
|-|-|
|ルートノードの削除|禁止。操作自体を受け付けない|
|循環参照となる移動|禁止。移動をキャンセル|
|不正なJSON読込|エラーメッセージを表示し、現在の状態を維持|
|必須プロパティの空|インスペクタで警告表示（強制エラーにはしない方針も可）|
|深すぎるネスト|推奨最大深度を設け、超える場合は警告（初期は制限なしでも可）|
|存在しないノードへの操作|無視または状態をリセット|
|DB接続失敗|エラーメッセージを表示し、編集中データは可能な範囲で保持|
|保存競合（同時更新）|初期は後勝ち（簡易）。必要に応じてupdated_atによる楽観ロックを検討|
|存在しないIDの取得|404相当のエラーを表示|
|バリデーションエラー|API側で最低限の構造チェックを行い、不正データは保存しない|

## 10. 実行環境設計

コンテナ構成
- app：Next.jsアプリケーション（フロント＋API）
- db：PostgreSQL

主な方針
- Docker Composeで app と db を起動
- アプリは環境変数でDB接続情報を受け取る
- 開発時はボリュームマウントでホットリロード可能とする
- DBデータはボリュームで永続化
- 初期スキーマ適用はマイグレーション（または起動時スクリプト）で行う

環境変数
- データベース接続URL
- 必要に応じてポートや認証情報
